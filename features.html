Step 2

Must-have features, with prompts to copy

These are the features that make a personal app safe and pleasant to live with. Add them while the app is still an Artifact, one prompt at a time, and test each before moving on.

Order matters a littleDo the secure login before the others: once data is encrypted, every later feature (logs, archives, backups) is automatically stored encrypted too.

1. Mobile friendly

Most people will open the app on a phone. Ask for it explicitly; don't assume.

Prompt: mobile friendly
Make the whole app work well on phones:
- Single column below 640px wide, no sideways scrolling
- Buttons and tap targets at least 44px high
- Numbers right-aligned and in tabular figures so columns line up
- Pop-ups fit the screen and scroll inside themselves
- Use the numeric keyboard for number fields (inputmode="numeric" or "decimal")
Then tell me anything you couldn't make work on mobile.

2. Secure login with real encryption

A PIN screen on its own only hides the page; anyone who can read the stored data still can. Ask for the data itself to be encrypted with a key made from the PIN, so the server and the storage only ever see scrambled data.

Prompt: encrypted PIN login
Add a secure PIN login:
- Store the data only as AES-256-GCM ciphertext. Derive the key from the PIN with PBKDF2-SHA256 (1,000,000 iterations, random salt). Never store the PIN or a hash of it; a wrong PIN simply fails to decrypt.
- First run: ask the user to choose a PIN (and confirm it), and warn that it cannot be recovered.
- Auto-unlock as soon as the full PIN is typed (no need to press Enter).
- On touch screens, show an on-page number keypad (1-9, Clear, 0, delete) instead of relying on the phone keyboard.
- A Lock button, and auto-lock back to the PIN screen after 30 minutes with no activity. Locking must clear the decrypted data and the key from memory.
Pick a strong enough PINOnce the site is public, anyone can download the encrypted data and try PINs offline. Each guess is slowed down by the 1,000,000 iterations, but a 4-digit PIN has only 10,000 possibilities. Use 6 to 8 digits for the unlock PIN.

For dangerous actions (like resetting a month), add a second PIN:

Prompt: second PIN for risky actions
"Start New Month" should need its own PIN, separate from the unlock PIN.
Ask the user to choose it the first time, and store only a salted PBKDF2 hash of it,
inside the encrypted data (never in the page source).

3. Transaction log

A log answers "who changed what, and when?" and makes mistakes easy to spot.

Prompt: transaction log
Keep a transaction history of every saved change: date/time, a plain-English description
("Update Rent from $1,200.00 to $1,250.00") and who made it.
Store it inside the encrypted data, keep the last 60 days, and show it in a
"Transaction History" pop-up grouped by day (Today, Yesterday, then dates), newest first.

4. Archive data (monthly history)

Archiving freezes a period so you can look back at it, and lets the live view start fresh.

Prompt: monthly archive
Add a "Start New Month" button that:
1. Asks "Are you sure?" and reminds the user to check the figures are final.
2. Lets them pick which month to save it as (default: last month early in the month, this month later on).
3. Saves a frozen, read-only copy of the whole budget to "Budget History", keeping up to 10 years (120 months).
4. Then resets the daily amounts to $0.00 but keeps the regular lines, income and monthly bills.
Lines added during the month are shown ticked to carry over; the user can untick any they want removed.
Add a "Budget History" button with a month picker (grouped by year) that shows any saved month, view only,
and lists the current month first as "current, running values".

5. Reports (PDF)

Prompt: PDF reports
In Budget History add a "Save as PDF" button for the selected month (current or archived).
Build the PDF in the browser with jsPDF and jspdf-autotable from cdnjs: A4, a summary table,
then a table per person with every line and the totals, plus "Created <date> · Page X of Y" in the footer.
Don't use window.print(); it is blocked inside Artifacts.

6. Export and import of the site data

This is the feature that lets you move data from the Artifact to the live site, keep your own offline copies, and recover from anything. Add it before you go live.

Prompt: export / import (give this to Claude or any developer)
Add data export and import to the app:

Export
- An "Export Backup" button (visible only after unlocking) that downloads a JSON file named
  "<App name> backup YYYY-MM-DD.json".
- The file contains the encrypted document exactly as stored, never the PIN or decrypted data:
  { "type": "<app>-backup", "v": 1, "exportedAt": "<ISO date>", "doc": { v, kdf, iter, salt, iv, ct } }
- Inside a claude.ai Artifact, save it through the "downloads" capability; on a normal website,
  use a Blob and an <a download> link.

Import
- On the first-run screen (when no data exists yet) show "Import a backup file" next to "Create new".
- Accept the backup format above, or a bare { salt, iv, ct, iter } document.
- Ask for the unlock PIN, prove it by decrypting the file before saving anything,
  then store the document unchanged so the same PIN keeps working.
- Show clear errors for: not a backup file, wrong PIN, server refused.

Keep the stored document format identical between the Artifact version and the website version,
so a backup from one imports into the other.

Also worth having

  • Confirm before saving. A "Save changes?" pop-up that repeats exactly what will change.
  • Who made the change. On your own site there's no Claude sign-in, so ask for a simple name picker on the unlock screen.
  • Save status. "Saving…", "All changes saved" and clear error messages, so nobody wonders if it worked.
  • Conflict handling. If two devices edit at once, the second save should be refused with a message and the latest figures reloaded, rather than silently overwriting.
